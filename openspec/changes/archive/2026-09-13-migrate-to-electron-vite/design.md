## Context

Ver `proposal.md` - Why. Estado atual relevante para esta migração:

- **Bootstrap**: `main.js` na raiz chama `MainMenu()` e `MainWindow('index.html')` (`src/components/Main`). `MainWindow` cria um único `BrowserWindow` com `nodeIntegration: true` / `contextIsolation: false` e `openDevTools()` sempre ligado.
- **Canal main → renderer**: tudo passa por uma única instância de `electron-store` (`src/components/Main/Window/index.js`, `Menu/index.js`, e o `<script>` inline em `index.html`). O main grava `{ view, nodes, edges }` ou `{ view: 'rootUnitSelection', projectUnits, projectDir }`; `reloadMainWindow()` (via `webContents.fromId(mainWindowId)`) recarrega a janela; o renderer lê a store no carregamento da página e decide o que desenhar. A store é limpa no evento `close` da janela.
- **Renderer**: `index.html` tem um único `<script>` inline que faz `require('fs')`, `require('path')`, `require('vis-data')`, `require('vis-network')`, `require('electron-store')` diretamente no processo de renderização - só possível com `nodeIntegration: true`. Ele também lê arquivos `.pas` do disco (`selectRootUnit`) diretamente no renderer para expandir o grafo a partir da Root Unit escolhida.
- **Camada de modelo** (`src/model/**`): pura, sem `require('electron')`, testada via Jest. Fora do escopo desta migração.
- **Empacotamento**: hoje inexistente - só `electron .` via script `start`. Não há Forge, não há Vite, não há build de produção.

## Goals / Non-Goals

**Goals:**
- Trocar o scaffold manual pelo gerado por `npx create-electron-app@latest --template=vite` (Electron Forge + Vite, processos `main`/`preload`/`renderer` com configs Vite próprias).
- Preservar 100% do comportamento observável hoje existente: File > Open (grafo de 1 nível), File > Open Project (seleção de Root Unit + escopo de uses + expansão recursiva do grafo).
- Substituir o par `nodeIntegration:true`/`contextIsolation:false` + `require()` direto no HTML por `contextIsolation:true` + `preload.js` com `contextBridge`, como o template Vite já assume.
- Substituir o "canal" `electron-store` como blob lido no load da página por comunicação IPC explícita (`ipcMain.handle`/`ipcRenderer.invoke` via preload), que é o padrão idiomático do template Forge+Vite.
- Manter `src/model/**` e `src/test/**` intactos (sem `require('electron')`, sem mudança de comportamento, suíte Jest continua passando sem alteração).

**Non-Goals:**
- Não é objetivo desta mudança introduzir novas funcionalidades de UI/UX, novas telas, ou alterar o parsing/expansão de grafo.
- Não é objetivo migrar para um framework de UI (React/Vue/etc.) - o template `vite` puro (JS vanilla) é suficiente; o app não tem estado de UI complexo o bastante para justificar isso agora.
- Não é objetivo configurar `make`/`publish` (instaladores por SO) nesta mudança - "empacotável" (`package`/`make` funcionam) é suficiente; distribuição fica para uma mudança futura, se necessária.
- Não é objetivo migrar `electron-store` para outra lib de persistência. **Atualizado na implementação**: com o canal main↔renderer migrando para IPC (Decision 2), deixou de existir qualquer necessidade de estado persistido entre "reloads" de página (o app não recarrega mais a página para navegar entre telas), então `electron-store` foi removida por completo em vez de restrita ao processo main - não há mais nenhuma dependência de persistência no projeto.

## Decisions

**1. Copiar o projeto atual inteiro para uma pasta de backup `pascal-dependency-viewer-bck/` dentro da própria raiz do repositório (subpasta não versionada, não um diretório externo), gerar o scaffold `create-electron-app@latest --template=vite` do zero diretamente na raiz do repositório (substituindo o conteúdo atual, preservando `.git`), e então trazer de volta o código da cópia temporária para dentro da nova estrutura gerada.**
Rodar o gerador oficial direto no lugar do projeto garante que as configs do Forge (`forge.config.js`) e do Vite (`vite.main.config.mjs`, `vite.renderer.config.mjs`, `vite.preload.config.mjs`) fiquem exatamente como a ferramenta as produz, sem risco de divergência de uma montagem manual por cima do projeto existente. A cópia temporária funciona como referência completa e rede de segurança: nada do código atual se perde, ele só é portado (arquivo por arquivo) para dentro da nova estrutura depois que ela já existe, validando cada porção (ex.: `npm test` logo após portar `src/model/**`) antes de seguir para a próxima. Estar dentro da raiz do repositório (em vez de em um diretório externo) facilita comparar lado a lado os arquivos antigos e novos durante o porte, mas exige disciplina para nunca `git add` essa pasta antes de ela ser removida (ver Risks). Alternativas consideradas: (a) adicionar `vite`/`@electron-forge/cli` manualmente ao `package.json` atual - descartada por exigir replicar de memória uma configuração que o gerador já acerta; (b) gerar o scaffold só para inspecionar a estrutura em um diretório à parte e depois montar manualmente as configs por cima do projeto atual (abordagem inicial deste design) - descartada porque ainda corria o risco de a montagem manual divergir do scaffold real; (c) manter a cópia de backup fora do repositório - descartada em favor de mantê-la dentro (mais simples de navegar durante o porte), com a mitigação de nunca commitá-la.

Passos 1-3 do Migration Plan abaixo (backup, geração do scaffold, checagem de versão) já foram executados manualmente: `pascal-dependency-viewer-bck/` existe na raiz com o código antigo completo, o scaffold já foi gerado (histórico do `.git` preservado, com um commit `temp` registrando o estado pós-scaffold), e a versão do Electron trazida pelo scaffold (`44.3.0`) já coincide com a que o projeto usava (`^44.3.0`), então não há decisão de versão pendente.

**2. Migrar o canal main↔renderer de "electron-store como blob + reload da janela inteira" para IPC (`ipcMain.handle` / `ipcRenderer.invoke`, expostos via `contextBridge` no preload).**
O modelo atual (gravar no store, chamar `reloadMainWindow()`, o renderer relê tudo do zero no load) é um efeito colateral de não ter IPC nem preload configurados - reload de página inteira para navegar entre "seleção de Root Unit" e "grafo" é mais pesado e mais difícil de depurar que uma resposta IPC direta. Com `contextIsolation: true` (exigido pelo template), o `require('electron-store')` direto no `<script>` do HTML deixa de ser possível de qualquer forma, então a mudança é necessária, não só desejável. Alternativa considerada: manter `electron-store` como canal e só adicionar um preload que reexpõe `store.get`/`store.set` via `contextBridge` - descartada porque perpetuaria o acoplamento a um blob global e o padrão de "reload da janela para navegar de tela", quando o próprio template já indica IPC como o caminho correto.
Superfície de IPC proposta (nomes ilustrativos, a refinar em `tasks.md`/implementação):
- `openFile` (renderer → main): dispara o diálogo de abrir `.pas`, main faz o parsing (`getUnitName` + `selectUsesFromSource` + `mountDependenceGraphStructure`) e retorna `{ nodes, edges }` para o renderer desenhar.
- `openProject` (renderer → main): dispara o diálogo de abrir `.dpr`, main faz `parseDprSource` e retorna `{ projectUnits, projectDir }`.
- `expandFromRootUnit` (renderer → main, com `{ projectDir, projectUnit, projectUnits, scope }`): main lê os arquivos `.pas` necessários do disco (hoje feito no renderer via `fs.readFileSync`) e roda `expandDependencyGraph`, retornando `{ nodes, edges }`.
Mover a leitura de arquivo para o main também resolve, de graça, o problema de `fs`/`path` não estarem mais disponíveis no renderer depois que `nodeIntegration` for desligado.

**3. Reescrever o `<script>` inline de `index.html` como um módulo JS de renderer (`src/renderer.js` ou equivalente do template), importado via `<script type="module" src="...">`, mantendo as mesmas funções (`renderGraph`, `selectRootUnit`, `renderRootUnitList`, `renderRootUnitSelection`) como funções puras de manipulação de DOM que chamam a API exposta pelo preload em vez de `require` direto.**
O template Vite já espera um entry point de renderer processado por Vite (permite `import` ES module de `vis-network`/`vis-data`, hot-reload em dev). Alternativa considerada: manter tudo em um único `<script>` inline dentro do HTML gerado - descartada porque o Vite processa/bundla a partir de um arquivo de entrada JS, não de um `<script>` inline, e perderíamos HMR e tree-shaking.

**4. Desligar `openDevTools()` automático do `BrowserWindow` (ou condicioná-lo a modo dev), já que o template Forge+Vite tem seu próprio fluxo de dev server.**
Hoje `mainWindow.webContents.openDevTools()` é chamado incondicionalmente em `Window/index.js:17`. O template Forge+Vite já abre em modo dev de forma própria; manter DevTools sempre abertos também em produção não é desejável. Tratado como ajuste incidental, não como mudança de comportamento visível ao usuário final do fluxo de negócio (parsing/grafo).

## Risks / Trade-offs

- [Risco] Perder alguma sutileza do fluxo atual de `electron-store` (ex.: limpeza no `close` da janela, id da janela salvo para reload) ao migrar para IPC → Mitigação: mapear cada leitura/escrita de store hoje existente (`view`, `nodes`, `edges`, `projectUnits`, `projectDir`, `mainWindowId`) para uma chamada IPC ou estado local do renderer antes de remover o código antigo, e só remover a pasta de backup `pascal-dependency-viewer-bck/` de referência depois que o novo fluxo estiver validado manualmente (File > Open e File > Open Project) na skill `run`.
- [Risco] Gerar o scaffold diretamente na raiz do repositório sobrescreve/apaga arquivos do projeto atual (`main.js`, `index.html`, `src/**`) antes de serem portados → Mitigação: só rodar o gerador depois de confirmar que a cópia para `pascal-dependency-viewer-bck/` está completa (feito: `pascal-dependency-viewer-bck/` contém `main.js`, `index.html`, `jest.config.js`, `LICENSE`, `package.json`/`package-lock.json` antigos e todo `src/components|model|test`); a pasta de backup nunca é apagada antes da validação final (seção 5 de `tasks.md`) passar.
- [Risco] `npx create-electron-app@latest` recusa rodar em diretório não vazio — confirmado experimentalmente que isso vale mesmo quando só existe a pasta `.git` (mensagem: "The specified path ... is not empty") → Mitigação (validada experimentalmente e é o que de fato aconteceu ao gerar o scaffold já presente na raiz): mover `.git` para fora da raiz antes de rodar o gerador (ou esvaziar a raiz de outra forma que satisfaça o gerador), rodar `create-electron-app`, descartar o `.git` novo que o gerador sempre inicializa e restaurar o `.git` original. O histórico foi preservado (`git log` mostra os commits originais mais um commit `temp` do estado pós-scaffold); `git status` mostra os arquivos antigos como removidos e os novos do scaffold como não rastreados, resolvido pelos commits desta migração.
- [Risco] A pasta de backup `pascal-dependency-viewer-bck/` vive dentro da árvore do repositório e aparece como não rastreada (`??`) no `git status` → Mitigação: nunca rodar `git add -A`/`git add .` enquanto ela existir; adicionar `pascal-dependency-viewer-bck/` ao `.gitignore` (ou removê-la do `.gitignore` do template se ele já a listar) enquanto durar o porte, e conferir `git status` antes de cada commit da migração para garantir que ela não foi incluída.
- [Risco] `contextIsolation: true` quebra a expectativa implícita de `require()` direto no HTML em qualquer ponto do código que não tenha sido migrado (ex.: algum uso futuro esquecido) → Mitigação: buscar por `require(` dentro de `index.html`/renderer novo antes de considerar a migração concluída; o preload deve ser a única porta de entrada para APIs Node/Electron no renderer.
- [Risco] Divergência entre a versão do `electron` já usada (`^44.3.0`) e a versão que o scaffold `create-electron-app@latest` traz por padrão → Já verificado: o scaffold gerado trouxe `electron@44.3.0`, igual à versão já fixada no projeto (`^44.3.0`), então não há decisão de upgrade/downgrade pendente nesta migração.
- [Trade-off] Empacotamento (`make`/`publish`) fica fora do escopo (ver Non-Goals) - aceito porque o objetivo desta mudança é a base de build/dev (Vite + IPC seguro), não distribuição; pode virar uma mudança OpenSpec futura.

## Migration Plan

1. ✅ Copiar todo o conteúdo atual do repositório (exceto `.git`) para a pasta de backup `pascal-dependency-viewer-bck/` dentro da própria raiz do repositório, como referência completa e rede de segurança antes de qualquer alteração destrutiva. (Feito.)
2. ✅ Mover `.git` para fora da raiz do repositório, apagar os demais arquivos/pastas de working tree (já seguros em `pascal-dependency-viewer-bck/`), rodar `npx create-electron-app@latest --template=vite` na raiz (agora vazia) para gerar do zero a estrutura de Forge+Vite (`forge.config.js`, `vite.main.config.mjs`, `vite.renderer.config.mjs`, `vite.preload.config.mjs`, novo `package.json`), descartar o `.git` novo que o gerador cria e mover o `.git` original de volta para a raiz. (Feito - `forge.config.js`, `vite.*.config.mjs` e `src/{main,preload,renderer}.js` já existem na raiz; `git log` mostra o histórico original mais um commit `temp`.)
3. ✅ Comparar a versão de `electron`/Forge trazida pelo scaffold com a atual (`^44.3.0`) e decidir se atualiza ou fixa a versão; confirmar que `npm start` abre a janela padrão do template antes de portar qualquer código. (Feito - scaffold trouxe `electron@44.3.0`, igual à versão já usada; falta apenas reconfirmar `npm start` já com as dependências instaladas, se necessário.)
4. Trazer `src/model/**` e `src/test/**` de volta da pasta de backup `pascal-dependency-viewer-bck/` para o novo projeto, sem alteração de caminho ou conteúdo, e rodar a suíte Jest (`npm test`) para confirmar que continuam verdes.
5. Portar `src/components/Main/**` (da pasta de backup `pascal-dependency-viewer-bck/`) para o novo entry point `main` do template, trocando `electron-store`+reload por handlers IPC (`ipcMain.handle`) para `openFile`, `openProject` e `expandFromRootUnit`.
6. Criar `preload.js` expondo via `contextBridge` só as três chamadas IPC acima (nenhuma superfície genérica tipo `require` cru).
7. Portar o `<script>` inline do `index.html` antigo (na pasta de backup `pascal-dependency-viewer-bck/`) para o entry point `renderer` do novo template, chamando a API exposta pelo preload em vez de `require` direto; manter os mesmos ids de elemento (`rootUnitSelection`, `rootUnitFilter`, `usesScopeControl`, `rootUnitList`, `mynetwork`) e a mesma lógica de exibição/ocultação de telas.
8. Validar manualmente via skill `run`: File > Open em um `.pas` avulso, depois File > Open Project + seleção de Root Unit com os dois escopos de uses (`interface` e `interface+implementation`).
9. Remover a pasta de backup `pascal-dependency-viewer-bck/` de referência (ou movê-la para fora do repositório) só depois que o passo 8 passar, junto com qualquer dependência que tenha ficado órfã no `package.json`.
10. Atualizar `CLAUDE.md` para descrever a nova divisão de processos (main/preload/renderer, Vite, IPC) e os novos comandos (`npm start` via Forge, `npm run package`/`npm run make` se configurados).

Não há dado persistido entre versões do app (a `electron-store` só guarda estado efêmero de navegação, limpo no fechamento da janela), então não há plano de rollback de dados - reverter é restaurar o repositório a partir da pasta de backup `pascal-dependency-viewer-bck/` (ou do commit/branch anterior à migração) enquanto ela ainda existir.
